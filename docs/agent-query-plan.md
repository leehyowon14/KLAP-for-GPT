# Agent 중심 조회 API 계획

상태: 설계안. 런타임 구현·배포 전.

기준: KLAP-for-GPT `555ee9a`, KLAP-core `68cb7d4`.
목표는 답변의 정확성을 유지하면서 도구 선택, 모델에 전달되는 데이터, 상세 조회 왕복을 줄이는 것이다.

## 1. 확정한 원칙

1. **개수로 조회 범위를 정하지 않는다.** 새 Agent 조회 계약에는 `limit`, `top_k`, `max_results`, `page_size`, `offset`, 묶음 개수 인수를 두지 않는다. 전달해도 무시하지 않고 잘못된 인수로 처리한다.
2. **의도로 조회한다.** 다음 시작, 지금 수강 가능, 기간 내 마감처럼 질문에 대응하는 선택 규칙을 서버가 적용한다.
3. **표시할 개수는 Agent가 정한다.** 사용자가 세 개만 알려 달라고 해도 서버에는 의미 있는 조회 범위를 전달한다. Agent는 받은 결과에서 세 개를 소개하면서 필요하면 전체 후보 수를 알린다.
4. **처음에는 판단에 충분한 요약을 반환한다.** 제목만 보고 다시 조회해야 하는 과도한 축약도 피한다. 날짜·완료 여부·불확실성 등 답변의 근거는 요약에 남긴다.
5. **상세는 선택한 ID들을 묶어서 조회한다.** 항목마다 도구를 한 번씩 호출하는 흐름을 기본으로 삼지 않는다.
6. **누락·미확인·전송 중단을 빈 결과와 구분한다.** 부분 결과로 전체·최초·없음을 단정하지 않도록 응답 계약과 스킬을 함께 바꾼다.
7. **질문의 범위와 전송 용량을 분리한다.** 큰 결과는 서버가 나누어 보내며, Agent가 크기를 지정하지 않는다. 이어받기는 같은 조회 결과를 계속 읽는 작업이다.

## 2. 의도별 도구 설계

기존 도메인별 도구 이름을 유지하고 조회 의도를 명시한다. 자유 형식 필터 DSL이나 임의의 도구 실행을 묶는 범용 batch API는 만들지 않는다.

### 강의: `klap_lectures`

| `intent` | 질문 예시 | 선택 규칙 |
| --- | --- | --- |
| `next_opening` | 다음에 열리는 강의는? | 현재 이후 시작하는 미완료 후보에서 가장 이른 시작 시각을 찾고, **그 시각의 강의 전체** 선택 |
| `available_now` | 지금 들을 수 있는 강의는? | 기간이 유효하고 현재 수강 가능하며 미완료인 강의 |
| `due_in_period` | 이번 주에 마감되는 강의는? | 완료되지 않았고 지정 기간 안에 종료되는 강의. 아직 시작하지 않은 강의도 포함 |
| `unfinished` | 아직 안 들은 강의는? | 완료가 확인되지 않은 강의 전체. 예정·진행 중·기간 종료를 구분하여 반환 |
| `completed` | 수강 완료한 강의는? | 완료가 확인된 강의 |
| `overview` | 이번 학기 강의를 보여줘 | 해당 범위의 강의 전체 요약 |

공통 범위는 `term`, 선택적인 `course_ids`, 의도에 필요한 `period`로 한정한다.
서버는 `2026-2`와 `2026,2`를 같은 학기로 정규화하고 실제 적용한 학기를 응답한다.
`course_ids`는 조회 도구가 준 정확한 ID만 받으며, 여러 과목을 한 번에 지정할 수 있다.

기간은 `today`, `this_week`, `next_week`, `next_7_days`, `custom`을 지원한다.
`custom`일 때만 ISO 8601 `from`, `until`을 받는다. 기간 필터는 `[from, until)`이며,
날짜만 지정하면 Asia/Seoul 기준으로 해석한다. 주간은 월요일 00:00부터 다음 월요일 00:00까지다.
첫 페이지에서 기준 시각을 한 번 고정하고 응답에 정규화한 구간을 표시한다.
현재 수강 가능 여부의 시작·종료 경계는 KLAS-core의 수강 검증 정책과 일치시킨다.
의도와 맞지 않는 인수는 무시하지 않고 오류로 반환한다.

### 과제·공지·마감·검색

| 도구 | 의도·범위 | 기본 응답 |
| --- | --- | --- |
| `klap_assignments` | `pending`, `due_in_period`, `overdue`, `submitted`, `overview` | 제목, 과목, 시작·마감, 제출 상태 |
| `klap_notices` | `recent`, `in_period`, `overview` | 제목, 과목, 게시 시각, 고정 여부, 첨부 존재 여부 |
| `klap_due` | `next_deadline`, `in_period`; 과제·강의·학사일정 종류 선택 | 종료·마감 기준 통합 요약. 강의 시작 질문에는 사용하지 않음 |
| `klap_search` | 검색어, `kinds`, 학기·과목·기간 | 일치한 항목의 요약과 검색한 범위 |

`recent`는 개수 기준의 최신 N개가 아니라 최근 7일 구간이다. 다른 기간은 `in_period`로 지정한다.
`due_in_period`, `in_period`에는 기간이 필요하다. `next_deadline`도 동일한 최단 마감 시각의 항목 전체를 선택한다.
학사일정처럼 완료 상태가 적용되지 않는 종류는 `not_applicable`로 구분한다.

초기 검색은 현재 코어가 지원하는 제목·과목명 등 메타데이터 검색으로 한정하고 `searched_fields`를 표시한다.
본문까지 검색했다고 표현하지 않는다. 본문 내용이 필요한 후보는 상세 조회로 확인한다.
전체 본문 검색과 별도 색인은 이번 범위에 넣지 않는다.

## 3. 네 개를 봐야 하는데 세 개만 보는 문제 방지

예: A·B·C·D가 모두 같은 가장 이른 시각에 시작한다.

```json
{
  "term": "2026,2",
  "intent": "next_opening"
}
```

서버는 A·B·C·D 모두를 선택한다. Agent가 임의로 개수를 정하거나, 첫 세 항목을 받은 후 스스로 최솟값을 계산하지 않는다.
처리 순서는 **조회 범위 확정 → 모든 대상 과목 조회 → 상태·기간 판정 → 의도별 묶음 선택 → 요약 → 전송 분할**이다.
마지막 전송 분할 때문에 선택 결과 자체가 달라져서는 안 된다.

묶음이 전송 예산보다 크면 같은 선택 결과를 이어받는다. 응답의 `page.complete=false`와 `next_cursor`를 확인하기 전에는 묶음이 끝났다고 판단하지 않는다.
‘같은 시각’은 정규화된 실제 타임스탬프가 같은 경우다. 같은 날짜라는 이유만으로 묶지 않는다.
‘오늘 열리는 강의’는 기간 조회이고 ‘다음에 열리는 강의’는 최소 시작 시각 조회다.

완료 여부와 수강 가능 여부를 별도로 정규화한다. 아직 열리지 않았다는 이유로 미완료 후보에서 제외하지 않는다.
시작 시각이나 완료 여부를 알 수 없는 항목은 `unknown`으로 보존한다. 임의의 0%, 미완료, 완료 값으로 채우지 않는다.
알 수 없는 값이 최솟값이나 일치 여부에 영향을 줄 수 있으면 `selection.status=uncertain`으로 반환한다.
기간을 모르는 항목을 몰래 제외하고 ‘가장 빠름’이나 ‘없음’을 확정하지 않는다.

## 4. 요약과 상세의 경계

| 단계 | 포함 | 이후 조회로 미루는 정보 |
| --- | --- | --- |
| 목록 요약 | stable ID, 제목, 과목 참조, 관련 날짜, 정규화한 완료·제출·수강 가능 상태 | 본문, 원본 HTML, 재생 URL, 내부 식별자, 제출물 본문, 점수·피드백 |
| 항목 상세 | 요청한 본문 또는 학습 상태·제출 조건·첨부 메타데이터 | 요청하지 않은 상세 영역과 파일 본문 |
| 긴 본문 이어읽기 | 이어받은 원문 구간, 구간 식별과 완료 여부 | 아직 전달하지 않은 본문 |

반복되는 과목 이름과 학기는 응답 상단의 과목 사전에 한 번만 두고 항목은 `course_id`로 참조한다.
필드 이름은 읽을 수 있게 유지하며 토큰 절감을 위해 알 수 없는 한 글자 약어로 바꾸지 않는다.
동일한 뜻의 값과 긴 상태 설명을 반복하지 않고, 상태 코드와 짧은 설명을 사용한다.
학교에서 가져온 본문은 모델이 새로 만든 요약으로 대체하지 않는다. 필요한 원문을 명시적인 구간으로 전달한다.
잘린 제목·본문이 있다면 잘린 사실과 이어받기를 표시한다.

요약만으로 날짜·개수·진행 상태 질문에 답할 수 있어야 한다. 본문 요약이나 제출 방법처럼 상세가 필요한 질문에서만 다음 단계로 간다.

### 선택한 항목 일괄 상세: `klap_get_items`

```json
{
  "ids": ["조회에서 받은 ID A", "조회에서 받은 ID B"],
  "sections": ["content"]
}
```

- 공지·과제·강의 stable ID를 지원한다. ID 목록은 조회할 정확한 대상을 뜻하며 개수 제한 인수가 아니다.
- `sections`는 `content`, `learning`, `submission`, `attachments` 중 필요한 영역만 지정한다.
- 공지의 `content`는 본문 텍스트, 과제의 `content`는 과제 설명, 강의의 `learning`은 세부 진도·수강 상태다. 강의의 `content`를 영상 전사로 해석하지 않는다.
- 지원하지 않는 종류·영역 조합은 항목별로 명시한다. 첨부 기능은 원본이 제공하는 메타데이터까지만 반환하며 다운로드를 실행하지 않는다.
- 단건도 같은 도구에 ID 하나를 넣어 처리한다. 서로 다른 종류의 ID를 섞어 요청할 수 있다.
- 중복 ID는 한 번만 읽고 첫 등장 순서를 유지한다. 결과를 입력 ID와 명확히 연결한다.
- 성공, 없음, 조회 실패, 아직 전달하지 않은 항목을 구분한다. 한 항목이 실패해도 나머지 성공 결과는 보존한다.
- 요청이 길면 서버의 바이트 예산으로 분할한다. 모든 요청 ID에 대한 결과 또는 미처리 상태를 알려야 하며, 일부 ID를 조용히 버리지 않는다.
- 긴 본문과 배치의 나머지도 같은 도구의 `cursor`로 이어받는다. 요청한 항목·영역, 본문 구간을 스냅샷에 고정하여 중복·누락 없이 진행한다.
- 같은 과목의 원본 목록을 여러 번 가져오지 않도록 내부에서 과목별로 묶고 재사용한다. 일괄 호출은 학교 요청을 무조건 병렬화한다는 뜻이 아니다.

## 5. 결과의 완전성을 읽을 수 있는 응답

기존 `kind`, `data`, `retrieved_at` 외피를 유지하되, v2의 `data`에 다음 의미를 둔다.
`schema_version=2`로 계약을 표시한다. 아래는 항목 본문을 생략한 메타데이터 예시다.

```json
{
  "query": {
    "intent": "next_opening",
    "term": "2026,2",
    "as_of": "2026-10-28T19:17:00+09:00"
  },
  "coverage": {
    "status": "complete",
    "requested_courses": 8,
    "succeeded_courses": 8
  },
  "selection": {
    "status": "verified",
    "matched_total": 4,
    "start_at": "2026-10-29T09:00:00+09:00"
  },
  "page": {
    "complete": true,
    "next_cursor": null
  }
}
```

다음 세 가지 상태를 분리한다.

- `coverage`: 대상 과목의 원본 조회가 전부 정상인지. 실패·과목 불일치는 `partial`이며 실패 과목과 이유 코드를 모델에도 전달한다.
- `selection`: 누락이나 미확인 날짜·상태 때문에 질문의 답을 확정할 수 없는지. 확정할 수 없으면 `uncertain`이다.
- `page`: 의도에 맞게 선택한 결과를 전부 전달했는지. 남아 있으면 반드시 이어받기 정보를 제공한다.

`matched_total`은 전체 범위가 검증된 경우에만 정확한 숫자다. 실패·불확실성이 있으면 `null`을 사용하고 확인한 수는 `observed_matches`로 구분한다.
이 숫자는 Agent가 결과를 설명하기 위한 응답 정보이며 요청 필터로 받지 않는다.
‘해당 항목 없음’은 원본 조회가 완전하고 선택이 검증되었을 때만 확정한다.
‘전체 항목을 보여줌’은 여기에 모든 페이지 수신까지 충족해야 한다.

정상 응답에는 과목별 성공 기록과 디버그 로그를 길게 반복하지 않는다. 원본 조회 시각 범위와 적용 조건은 간결하게 유지하고,
실패·불일치·판단 불가 정보는 모델에서 숨기지 않는다. `retrieved_at`은 응답 생성 시각이고 원본 조회 시각과 다름을 구분한다.

## 6. 전송 예산과 스냅샷

Agent가 지정하는 결과 개수·토큰 예산 인수는 두지 않는다. 서버의 초기 전송 예산은 직렬화된 도구 결과 32 KiB로 두고,
한글·긴 제목·첨부가 많은 입력으로 측정해 조정한다. 이는 토큰 수를 정확히 보장하는 값이 아니다.

첫 조회는 최신 원본을 조회한다. 선택한 결과와 기준 시각은 5분간 유지되는 스냅샷으로 이어받는다.
cursor는 계정·인증 주체·도구·필터·정렬·원본 버전에 묶인 opaque 값이며, 다음 요청은 cursor만 받는다.
필터 변경, 다른 계정의 cursor, 만료·재시작·메모리 회수는 명시적 오류다. 몰래 새 조회의 중간부터 이어가지 않는다.
같은 cursor의 재시도는 같은 페이지를 반환하고 정렬의 마지막 기준은 stable ID로 고정한다.

스냅샷은 한 조회의 전송 일관성을 위한 것이며 여러 과목을 같은 순간에 읽었다는 의미는 아니다.
상세 조회는 새로운 원본 조회 시각을 표시하며, 목록 이후 내용이 달라질 수 있다.
실제 수강 같은 변경 작업은 스냅샷의 수강 가능 판정을 믿지 않고 실행 시 다시 검증한다.

## 7. MCP 출력과 토큰 효율

- `structuredContent`: Agent 판단에 필요한 요약, 상태, 이어받기 정보.
- `content.text`: 결과 범위와 주의 사항을 알리는 짧은 문장. 같은 JSON 전체를 재출력하지 않는다.
- `_meta`: UI에서만 필요한 표현 정보. Agent 답변에 필요한 항목·오류·조건은 여기로 숨기지 않는다.

ChatGPT는 `structuredContent`와 `content`를 모델에 전달하며 `_meta`는 컴포넌트에만 전달한다.
짧은 텍스트 요약과 구조화 데이터를 함께 반환하는 방식은 [OpenAI 도구 결과 예시](https://developers.openai.com/plugins/reference#tool-results)에 따른다.
[MCP 2025-06-18 명세](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#structured-content)의
JSON 텍스트 병행 권고는 구형 클라이언트 호환성 목적이므로, portable 클라이언트는 별도 호환성 검증을 한다.
구형 클라이언트를 지원해야 할 때도 필터링한 최소 결과를 텍스트로 제공하고 ChatGPT 기본 경로에 전체 JSON 중복을 복원하지 않는다.

응답 토큰뿐 아니라 도구 스키마·설명·스킬, 필요한 후속 호출까지 합친 비용을 비교한다.
공통 문구는 스킬에 두고 도구 설명에는 구분 기준만 짧게 둔다. 일반 조회에서 불필요한 `klap_open` 선행 호출도 제거한다.
화면을 열어 달라는 요청일 때 `klap_open`을 사용하고, 계정 연결 문제는 실제 조회의 명시적 오류로 처리한다.

## 8. 정확성 선행 작업과 코어 경계

이전 검토에서 같은 KLAS 세션의 과목 선택과 목록 조회가 겹치면 다른 과목 응답이 오류 없이 제외되는 상황을 모의 테스트로 재현했다.
해당 모의 결과가 실제 19:08 누락의 원인을 확정하지는 않는다.

먼저 KLAP-core에서 과목 컨텍스트 변경과 해당 조회를 하나의 보호 구간으로 처리하고,
요청 과목과 응답 과목 불일치를 정상 빈 결과로 처리하지 않도록 한다.
MCP 조회·브라우저·이벤트 감시·수강 작업이 같은 세션을 사용하는 경로 전체에 적용한다.
긴 수강 작업 전체가 아니라 필요한 KLAS 요청 단위에 보호를 적용해 감시가 장시간 막히지 않게 한다.
별도 프로세스가 같은 세션을 공유하는 경우도 테스트하여 보호 범위의 한계를 확인한다.

과목별 성공·실패, 날짜·완료 상태 정규화, 의도 선택과 안정 정렬은 코어에 둔다.
MCP용 요약 직렬화·전송 예산·cursor 저장·도구 설명은 이 저장소에 둔다.
코어의 기존 CLI용 목록 API는 유지하고 새 결과형·조회 API를 추가하여 CLI와 KLAP_mac의 동작을 무단 변경하지 않는다.
코어 커밋을 먼저 배포 가능한 원격에 올리고 이 저장소의 submodule과 KLAP_mac의 코어 참조를 같은 커밋으로 맞춘다.

MCP Events 감시는 Agent의 의도별 필터나 전송 분할을 사용하지 않고 기존의 전체 콘텐츠 스냅샷을 사용한다.
원본 누락이나 부분 실패가 있으면 이벤트 기준선을 완전한 조회처럼 갱신하지 않는다.
이번 변경에 기존 공지 수정 이벤트 추가나 새로운 수강 자동화는 포함하지 않는다.

## 9. 구현 순서와 독립 커밋

각 행은 하나의 목적이며 테스트는 해당 구현과 함께 커밋한다. 더 작게 분리 가능한 행은 구현 시 추가로 나눈다.

| 순서 | 변경 단위 | 완료 기준 |
| --- | --- | --- |
| 1 | 코어의 세션·과목 응답 일치성 보정 | 동시 조회·원본 빈 목록·잘못된 과목 응답 구분 |
| 2 | 코어 강의 상태·시각·조회 범위 결과형 | 완료와 수강 가능 분리, unknown 보존 |
| 3 | 코어 강의 의도 선택 | next_opening 동시 시작 묶음과 기간 경계 검증 |
| 4 | MCP 공통 응답·스냅샷·이어받기 | 크기 제한 시에도 명시적 진행과 동일 결과 재시도 |
| 5 | 강의 도구 v2 어댑터 | 개수 인수 미노출·거부, 최소 요약 출력 |
| 6 | 코어 과제·공지 의도 조회 | 각 도메인별 별도 커밋과 테스트 |
| 7 | 과제·공지 MCP 어댑터 | 각 도메인별 간결한 요약과 품질 정보 |
| 8 | 공지·과제·강의 일괄 상세 | 공통 틀과 도메인 어댑터를 분리, 항목별 오류·본문 이어읽기 검증 |
| 9 | 마감·검색 어댑터 | 서로 별도 커밋, 의미 범위와 검색 필드 명시 |
| 10 | UI의 v2 응답·상세 지연 조회 | 목록·선택 수강·오류·추가 결과 탐색 동작 유지 |
| 11 | 도구 선택 스킬과 사용 문서 | 시작 질문에 due 미호출, 요약으로 충분하면 상세 미호출 |
| 12 | 플러그인 메타데이터와 릴리스 | 응답 스키마 갱신, 호스트 재스캔, 실연결 검증 |

Agent 조회 v2는 목록의 `data` 구조가 바뀌는 변경이므로 `0.2.0` 릴리스로 관리한다.
기존 안정 ID와 OAuth·Events 계약은 유지한다. 기존 단건 상세 도구는 한 릴리스 동안 호환 경로로 유지하고 새 스킬은 일괄 상세를 사용한다.
UI는 먼저 기존·새 응답을 모두 읽을 수 있게 준비하고, 새 UI 리소스 버전과 도구를 함께 전환한다.
단계별 커밋이 곧 운영 전환을 뜻하지는 않는다. UI와 필수 검증이 준비되기 전에는 v2 계약을 운영에서 활성화하지 않는다.
기존 대화의 캐시된 도구 스키마·앱 화면은 새로고침 또는 새 대화가 필요함을 릴리스에 명시한다.
되돌릴 때 서버·UI·플러그인 메타데이터·코어 참조를 같은 릴리스 묶음으로 복구하고, 임시 cursor는 명시적으로 만료시킨다.

## 10. 검증과 합격 기준

### 의미와 누락

- 가장 이른 같은 시각의 강의가 1개·4개·대량인 경우에 같은 선택 규칙을 유지한다.
- 제목이 같아도 stable ID가 다르면 보존한다. 중복 ID는 중복 조회·중복 결과를 만들지 않는다.
- 시작 시각 없음, 종료가 시작보다 빠름, 완료 상태 없음, 잘못된 진도, 동시 시작·종료 경계를 검증한다.
- 주간 경계·자정·KST와 UTC 표기·학기 구분자 차이를 검증한다.
- 정상 0개, 과목 일부 실패, 모든 과목 실패, 응답 과목 불일치를 서로 다른 결과로 확인한다.
- 요청에 개수·정렬·offset 인수를 추가해도 조용히 적용하거나 무시하지 않고 거부한다.

### 분할과 일괄 상세

- 전송 예산 경계 전후, 한글·이모지·긴 제목, 같은 시작 묶음의 중간 분할을 검증한다.
- cursor 재시도·만료·변조·필터 변경·권한 변경·서버 재시작을 검증한다.
- 페이지 사이에 학교 데이터가 바뀌어도 기존 스냅샷에 중복·누락이 발생하지 않는다.
- 혼합 종류·중복·삭제·잘못된 ID·부분 실패·긴 본문에서도 모든 요청 ID의 상태를 추적한다.
- 본문 구간을 합치면 원문과 일치하고 요약·누락을 완전한 본문으로 표시하지 않는다.
- UI가 사용하는 `structuredContent`, 단건 호환 경로, portable 클라이언트를 함께 확인한다.

### Agent 동작과 비용

| 질문 | 기대 경로 |
| --- | --- |
| 다음에 열리는 강의는? | lectures(next_opening) → 요약으로 답변. 결과가 작으면 도구 1회 |
| 지금 들을 수 있는 강의 세 개만 알려줘 | lectures(available_now) → Agent가 표시할 세 개 선택. 개수 인수 없음 |
| 이번 주 과제 마감은? | assignments(due_in_period, this_week) → 상세 없이 답변 |
| 이 공지들과 과제의 내용을 비교해줘 | 필요한 목록 요약 → 선택 ID 일괄 상세 → 비교 |
| 전체를 빠짐없이 정리해줘 | 의도 조회 → next_cursor를 끝까지 읽기 → 완전성 확인 후 답변 |

동일한 고정 fixture로 후보 누락률, 잘못된 확정 답변, 도구 호출 수, KLAS 요청 수, 실제 모델 입력 토큰,
직렬화 바이트, 서버 p50/p95를 비교한다. Agent 전체 지연은 도구 준비·도구 실행·답변 생성과 구분하여 별도로 측정한다.
구조화 데이터·텍스트·UI 전용 메타데이터의 전달 크기를 분리해 기록한다.

필수 기준은 의도별 정답 집합 일치, 누락의 명시, 요약 질문의 불필요한 상세 호출 제거다.
고정 fixture의 ‘다음 강의’ 입력 토큰을 기존 전체 목록 응답 대비 70% 이상 줄이는 것을 성능 목표로 삼되,
달성 여부는 구현 후 측정하고 필요한 정보를 버려 수치를 맞추지 않는다.
일괄 상세의 토큰과 후속 호출까지 합친 총비용도 함께 확인한다.
운영 KLAS의 실제 결과와 ChatGPT 도구 선택·렌더링은 로컬 테스트와 구분하여 최종 확인한다.
